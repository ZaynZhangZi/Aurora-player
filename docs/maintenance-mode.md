# 页面、功能开关与维护模式

## 使用方式

1. 使用管理员账号登录管理后台，进入「系统 → 页面与功能开关」。
2. 全站维护使用原有总开关；独立维护在列表中关闭相应项目的「开放」开关。
3. 左栏选择分区，中栏选择项目或切换开放状态，右栏编辑当前项目。页面分为内容、外观、预览；功能仅配置文字提醒和预览。
4. 开关、继承选项和批量操作直接自动保存；文案停止输入约 650 毫秒或离开输入框后自动保存，不需要再点击确认。顶部显示保存中、已保存、内容待补全或保存失败，用户端在下一次检查时同步。
5. 页面关闭后跳转 `/maintenance?from=原地址`；恢复后自动跳回原地址，保留查询参数。功能关闭后在当前页弹出维护窗口，页面和地址均保持不变。

目前有 50 个独立开关：

| 分组 | 覆盖范围 |
| --- | --- |
| 页面（11） | 首页、发现、曲风、搜索、歌单、专辑、歌手、个人中心、消息、动态、更新日志；兼容别名和带参数直链 |
| 账号与个人中心（4） | 登录、资料与绑定、云盘、听歌画像 |
| 播放器（7） | 播放、全屏歌词和可视化、AutoMix、音质、队列、歌词分享和导出、设置 |
| 发现与推荐（16） | 听歌识曲、MV、Banner、每日推荐、私人电台、场景电台、推荐歌单、最近播放、收藏、AI、精选、曲风浏览、新发行、排行榜、艺人目录、播客 |
| 消息与社交（7） | 私信、通知、发布与转发动态、评论、点赞、关注、话题 |
| 搜索（5） | 综合、歌曲、艺人、专辑、歌单搜索 |

全站维护优先于独立项目维护。多个项目同时关闭时，优先显示当前页面的维护内容，再显示当前操作或已打开功能的维护内容。
独立页面维护提供「返回可用页面」。功能维护弹窗可通过右上角关闭、Esc、点击遮罩或「我知道了」退出；关闭提示不会开放该功能，轮询不会重复打断用户，再次操作时仍会提示。全站维护时仍使用完整维护页。
关闭提醒后，已停用的搜索结果、发现栏目、首页推荐、云盘和消息区域会显示简短的不可用提示，缓存内容中的操作入口随之移除。栏目导航和其他开放功能可以继续使用。恢复开关后自动重新加载；上传、删除、发送等写入操作不会补发。

后台支持本分区搜索、开放 / 关闭状态筛选。底部批量按钮只影响当前分区或当前筛选结果，合并成一次自动保存。顶部统计使用服务端已保存状态，项目旁会标记正在同步或未同步。
保存过程中可以继续编辑和切换分区，请求按顺序提交，较早的响应不会覆盖新输入。保存失败会保留输入，显示「重试保存」，不会无限重试。空标题、未写完的图片地址等字段保留线上上次有效值，补全后自动提交，不阻止其他开关或有效字段保存。离开页面时会提交尚在等待的编辑，无须再次确认。

维护开关默认关闭。预计恢复时间只展示文案，不会按该时间自动关闭维护；应在实际恢复后关闭相应开关。
只有 `ROLE_ADMIN` 可以读取和修改管理设置。维护期间管理后台仍然可用。
错误页与管理后台不纳入用户端开关，避免关闭后无法恢复系统。

## 页面与提醒内容

不填自定义 HTML 时，使用浅色封套与唱片插画页面，手机端为纵向布局。支持自定义标题、说明、预计恢复时间、六位十六进制主题色和 HTTP(S) 背景图片地址。底部显示北京时间、下一次检查时刻和倒计时。

填写自定义 HTML 后，该内容取代默认维护页面主体。支持 HTML、CSS 和图片，最大 100,000 个字符。
内容在 `sandbox=""` 的 iframe 中展示，不能运行脚本、提交表单或操作父页面。
底部的自动检查提示和「立即检查」按钮始终保留。后台预览展示当前编辑内容，配置通过自动保存发布；切换预览不会额外提交请求。

功能关闭时使用屏幕中央的简洁提醒框，仅显示警告图标、标题、说明、恢复时间和操作按钮。功能提醒不渲染维护页、HTML、图片背景或唱片动画；旧配置中的这些页面字段会保留，但不会显示在提醒框内。「使用默认提醒」会使用功能名称和通用维护说明，也可取消后单独编辑文案。

## 检测与恢复

- 用户端启动时立即检查，随后统一在北京时间每分钟的 00、10、20、30、40、50 秒检查；不再从每个人进入页面的时刻各自计算 10 秒。
- 状态接口通过 `X-Maintenance-Server-Time` 响应头提供服务器 Unix 毫秒时间，跨域配置会暴露该头。用户端按请求往返时间估算时钟偏差，显示北京时间并校准检查时刻，设备时区或设备时钟快慢不会影响已校准的安排。
- 手动检查、重新联网和回到标签页会立即检查并重新对齐，保留统一的整 10 秒安排。标签页休眠导致定时器延迟时，会跳过错过的时刻，避免恢复后连续补发请求。
- 旧版接口或独立状态地址不提供校时头时，先按设备时钟对齐；需要服务器校时的独立状态源应同时返回上述头并通过 `Access-Control-Expose-Headers` 暴露，且禁止缓存。
- 单次请求 4 秒超时；同一时刻最多一个检查请求，手动检查也复用进行中的请求。
- 维护页持续轮询，并同步更新维护文案与页面配置。
- 网络错误、非成功响应或无效 JSON 不会被当作「维护结束」，会保留当前维护状态并重试。
- 首次检查失败且还没有取得维护状态时，允许正常打开网站，避免状态接口故障阻止访问。
- 初次访问已处于维护状态时，不挂载业务页面；已打开的业务页面则保留组件和路由状态。
- 收到 `enabled: false` 后恢复原页面，用淡出动画过渡；系统开启减少动态效果时不播放过渡动画。
- 独立项目的 `available: true` 表示正常开放，`false` 时页面跳转维护页、功能显示弹窗。
- 已打开的弹窗、歌词播放器、识曲和 MV 会响应开关变化；维护页不会被原生设置弹窗遮挡。
- 重新开放后，当前搜索、发现页栏目、云盘、听歌画像和消息会重新加载数据。写入和上传操作不会自动重复提交。
- 音乐播放被关闭时暂停播放，恢复后由用户主动继续，避免突然出声。
- 页面导航在加载组件前检查开关，覆盖站内链接、详情浮层和浏览器前进 / 后退；已有页面仍由全局维护层拦截。
- 交互拦截覆盖鼠标、触摸、键盘按下 / 松开、输入、表单提交、拖放和文件选择；页面维护同时隔离通过 Teleport 挂载到页面外层的业务弹窗。
- 业务请求发送前和返回时都检查维护状态；维护前发出的读取请求不会在维护期间重新填充可操作结果。搜索接口按查询类型匹配独立开关，综合搜索还检查综合搜索开关。
- 系统媒体控制、音质切换和歌词导出也检查维护状态，防止操作等待期间开启维护后继续执行。

用户端会拦截被关闭功能的操作和相关请求；后台管理服务始终保持可访问。开关用于维护展示和客户端操作控制，不替代服务端权限校验，也不会从接口报错自动推断需要开启维护。

## 服务端部署

需要一起发布用户前台、管理后台和 Java 服务端，旧的已打开用户页面需先加载过新版前台。

数据库使用独立的 `maintenance_config` 单行配置表，维护设置保存后可跨重启保留。
本次独立开关存放于该表已有的 `settings_json.targets` 中，已部署全站维护功能的环境不需要再建表或增加列。
旧配置不含 `targets` 时，各独立项目默认开放。旧版客户端只修改全站配置时，会保留已保存的独立开关。
必须发布包含 `TargetMaintenanceSettings` 的新版 Java 后端；仅更新前台或管理后台不能使新开关生效。
当前 `spring.jpa.hibernate.ddl-auto=update` 会自动创建该表。
关闭自动建表的环境，应在发布前执行：

`backend/backend/AuroraPlayer-Backend/database-migration-maintenance.sql`

接口：

| 方法 | 路径 | 权限 |
| --- | --- | --- |
| GET | `/api/v1/system/maintenance` | 无需登录 |
| GET | `/api/v1/admin/maintenance` | 管理员 |
| PUT | `/api/v1/admin/maintenance` | 管理员 |

状态响应禁止缓存。用户端状态检查不附带登录令牌。
`X-Maintenance-Server-Time` 仅作为响应头返回，不写入维护设置或数据库，现有 JSON 格式保持兼容。

独立开关配置示例（加入现有维护响应的 `targets` 字段）：

```json
{
  "page.search": {
    "available": false,
    "useGlobalPage": false,
    "title": "搜索升级中",
    "message": "我们正在升级搜索，其他音乐页面仍然开放。",
    "estimatedReturn": "今天 22:00",
    "accentColor": "#a78bfa",
    "backgroundUrl": "",
    "customHtml": "<h1>搜索维护中</h1>"
  },
  "feature.recognition": { "available": false, "useGlobalPage": true }
}
```

用户前台与管理后台的开关目录均为 `src/config/maintenanceTargets.json`，新增模块时应同步目录并接入入口和活动状态。回归测试会核对目录一致性和业务路由覆盖。

## 主服务完全停机时

默认状态地址为 `<内容后端地址>/api/v1/system/maintenance`，与已有内容后端共用配置和代理。
如果需要在 Java 服务或数据库完全停机时继续控制维护状态，可以在前台构建环境中设置：

```dotenv
VITE_MAINTENANCE_STATUS_URL=https://status.example.com/maintenance.json
```

该地址应部署在独立静态服务或 CDN，支持跨域 GET，并关闭缓存。支持直接返回 JSON，或现有的 `{ "code": 200, "data": ... }` 包装格式：

```json
{
  "enabled": true,
  "title": "系统维护中",
  "message": "正在恢复音乐服务，请稍候。",
  "estimatedReturn": "今天 22:00",
  "accentColor": "#a78bfa",
  "backgroundUrl": "",
  "customHtml": ""
}
```

使用独立地址后，应更新该地址的 JSON 来开启或结束维护；后台保存的配置只写入 Java 服务的数据库，不会同步发布到 CDN。
该功能需要浏览器能加载前台静态资源；整个站点的静态托管也停机时，需要由 CDN 或网关提供兜底页面。

## 验证

- 前台：`npm run build`、`npm test`；维护专项为 `node --test tests/maintenance.test.mjs tests/maintenance-access.test.mjs tests/maintenance-interaction.test.mjs`，覆盖 50 个开关在关闭提示后的持续拦截、搜索参数、迟到响应、多种交互和系统媒体控制。

- 服务端：`mvn -Dtest=MaintenanceControllerTest,SecurityConfigAuthTest test`（18 项通过）。
- 浏览器：在用户前台目录运行 `node tests/.maintenance-browser.mjs`。该脚本使用本机 Chrome、独立临时配置和模拟 API，检查真实 10 秒轮询、所有业务页面直链、独立功能入口、活动弹窗、已填充的搜索 / 发现缓存、云盘删除确认框、消息区域、历史返回、Teleport 隔离、恢复以及后台 50 个开关的预览与保存。设置 `MAINTENANCE_SCREENSHOTS=0` 可以只验证而不更新截图。
